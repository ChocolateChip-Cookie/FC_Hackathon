## 이 프로토타입이 다른 점

일반적인 RAG 데모는 "검색 후 생성"까지만 합니다. 여기에 셋을 더했습니다.

1. **거부** - 근거가 없으면 지어내지 않고 답변을 거부합니다.
2. **권한** - 역할에 따라 **검색 후보 자체를** 제한합니다. 신입은 급여 테이블을 검색조차 못 합니다.
3. **측정** - 골든셋 40문항으로 정답률·오거부율·함정 거부율을 **신뢰구간과 함께** 냅니다.

대형 RAG 프레임워크 4종(RAGFlow · Dify · LangChain · Langflow)의 소스를 대조한 결과,
1번은 저희만의 것이 아닙니다(RAGFlow가 더 정교합니다). 2번과 3번이 실제로 희소합니다.
근거는 [`CLAUDE.md`](CLAUDE.md) §1.1에 있습니다.

## 빠른 시작

```bash
git clone <this-repo>
cd FC_Hackathon
python -m venv .venv                  # 전용 가상환경 권장 (아래 주의 참조)
.venv\Scriptsctivate               # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt

cp .env.local.example .env.local     # 가진 키만 채우세요. 전부 비워도 됩니다.

python src/ingest.py                 # 인덱스 생성 (커밋된 인덱스가 있으면 생략 가능)
streamlit run app.py
```

**Windows 주의**: 이 저장소는 `python3`가 아니라 `python`을 씁니다.
PowerShell에는 `export`와 `VAR=x cmd` 문법이 없습니다. `$env:NAME="..."`를 쓰세요.

**전용 venv를 권장하는 이유**: 시스템 파이썬에 다른 도구가 깔려 있으면 의존성이 충돌합니다.
개발 머신에서 실제로 `streamlit`과 `fastapi`가 `starlette` 버전을 두고 충돌해
`streamlit run`이 기동하지 못했습니다. venv를 쓰면 이 문제가 없습니다.

### 키가 하나도 없어도 됩니다

`.env.local`을 비워도 **BM25 검색, 권한 필터 전수 검사, 검색 평가가 전부 그대로 돌아갑니다.**
이 프로젝트의 보안 축과 측정 축은 외부 서비스에 의존하지 않습니다.

| 가진 키 | 임베딩 | 가능한 검색 | 답변 생성 |
|---|---|---|---|
| **없음** | - | **BM25** | 안 함 (검색 결과만 표시) |
| `ANTHROPIC_API_KEY` | - | **BM25** | Claude |
| `UPSTAGE_API_KEY` | solar-embedding (2048차원) | dense / BM25 / 앙상블 | Solar |
| `OPENAI_API_KEY` | text-embedding-3-small (1536차원) | dense / BM25 / 앙상블 | GPT |
| **로컬 BGE-M3** (권장) | bge-m3 (1024차원) | dense / BM25 / 앙상블 | Ollama |

**Anthropic에는 임베딩 API가 없습니다.** 앤트로픽 키만 있으면 생성은 되지만 dense 검색은
불가능하고 BM25로 떨어집니다. 화면에 그 사유가 표시됩니다.

## 검증된 수치

아래는 전부 실제로 명령을 돌려 얻은 값입니다. 재현 명령을 함께 적었습니다.

### 권한 필터 - 전수 검사 (표본이 아니라 전량)

```bash
python eval/permission_matrix.py bm25
python eval/permission_matrix.py dense
```

| 역할 | 열람 가능 등급 | 32청크 중 차단 |
|---|---|---|
| 신입사원 | public | **19** |
| 일반 직원 | public, internal | **9** |
| 인사팀 | public, internal, confidential | **0** |

**청크 32 × 역할 3 = 96조합 전수 검사, 반례 0건.**
표본이 아니라 전량이므로 신뢰구간이 없습니다. 반례가 있거나 없거나 둘 중 하나입니다.

### 검색 방식 3종 비교

```bash
python eval/evaluate.py --compare        # LLM 비용 0
```

개발셋 21문항으로 임계값을 튜닝하고 **홀드아웃 19문항으로 보고**합니다.
고른 데이터로 성적을 보고하면 과적합이 성능으로 둔갑하기 때문입니다.

| 방식 | MRR | 정답률 | 함정 거부 | 오거부 |
|---|---|---|---|---|
| dense | 1.000 | 14/19 (74%, CI 51-88%) | 2/7 (29%) | 0/12 (0%) |
| bm25 | 1.000 | 14/19 (74%, CI 51-88%) | 2/7 (29%) | 0/12 (0%) |
| **ensemble** (alpha 0.8) | 1.000 | **15/19 (79%, CI 57-91%)** | 3/7 (43%) | 0/12 (0%) |

앙상블이 가장 높지만 **세 방식의 신뢰구간이 겹칩니다. n=19에서 "앙상블이 낫다"고 단정하지 않습니다.**

**MRR이 세 방식 모두 1.000입니다.** 답변 가능 문항에서 정답 문서가 항상 1순위였다는 뜻입니다.
즉 **검색 순위는 완벽하고, 실패는 전부 거부 레이어에서 납니다.** 이 사실이 어디를 고쳐야 하는지를
가리킵니다. 검색을 더 좋게 만드는 것은 의미가 없습니다.

함정 거부율이 낮은 것은 결함이 아니라 측정 결과입니다. 이 수치는 **검색 임계값(거부 1겹)만으로
잰 값**이며, 문서 어휘를 쓰면서 답이 없는 고난도 함정은 1겹을 통과합니다.
2겹(LLM 판정)이 필요하다는 정량적 근거입니다.

### 앙상블 가중치는 어떻게 정했나

```bash
python eval/evaluate.py --alpha-scan      # 개발셋만 사용, 홀드아웃 미사용
```

MRR로 alpha를 고르려 했으나 **모든 alpha에서 1.000이라 변별력이 없었습니다.**
대신 **분리도**(답변 가능 문항의 점수가 거부 문항의 점수보다 높은 쌍의 비율, 임계값과 무관)를 썼습니다.

| alpha | 0.0 | 0.3 | 0.5 | 0.7 | 0.8 | 0.9 | 1.0 |
|---|---|---|---|---|---|---|---|
| 분리도 | 0.727 | 0.755 | 0.800 | 0.827 | **0.836** | 0.836 | 0.836 |

0.8~1.0이 동점이라, 조항 번호·부서명 같은 정확한 어휘 일치를 위해 BM25 신호를 남기는
**낮은 쪽(0.8)**을 택했습니다.

**정직하게 밝힙니다**: alpha 0.5로 재면 홀드아웃 정답률이 16/19로 1문항 더 높았습니다.
그러나 홀드아웃을 보고 alpha를 되고르면 그것은 더 이상 홀드아웃이 아닙니다.
개발셋으로 고르고 홀드아웃 결과를 그대로 보고합니다. 1문항 차이는 n=19에서 잡음 범위입니다.

## 아직 검증되지 않은 것

정직하게 적습니다. 확인하지 않은 것을 확인했다고 쓰지 않습니다.

- **LLM 생성 경로가 한 번도 실행된 적이 없습니다.** API 키와 Ollama가 모두 없는 환경에서
  개발했습니다. 따라서 출처 표기, 인용 검증, 프롬프트 인젝션 방어는 코드만 있고 **미검증**입니다.
- 거부 임계값이 임베딩 백엔드마다 다릅니다. bge 외 백엔드의 값은 아직 스윕으로 확정하지 않았습니다.
- 관측성(Phoenix 트레이싱, `logs/` 스키마)은 미착수입니다.

## 설계상 바꾸면 안 되는 것

- **권한 필터는 검색 단계에서 적용합니다** (`src/store.py`의 chroma `where` 절).
  프롬프트에 넣고 답변에서 가리는 방식은 인젝션 한 번에 원문이 새어나갑니다.
- **거부 1겹은 LLM 호출 전에 일어납니다.** 결정적이고 비용이 0입니다.
- **청킹은 고정 길이가 아니라 `## 제N조` 헤딩 단위입니다.** 조항 번호를 그대로 출처로 쓰기 위해서입니다.
