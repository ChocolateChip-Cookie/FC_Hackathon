# On-premise RAG 구축 설계서

> 프로토타입은 외부 API로 구현했습니다. 이 문서는 동일한 시스템을 사내 폐쇄망으로 옮기는 설계입니다.
> 수치가 붙은 항목은 계산식을 함께 적었습니다. 실제 도입 전 자사 조건으로 재계산해야 합니다.

## 1. 왜 온프렘인가

사내 정보보안 정책(DOC-SEC-005 제3조)은 고객 개인정보, 소스코드, 미공개 재무자료를
외부 생성형 AI 서비스에 입력하는 것을 금지합니다.
그런데 온보딩 어시스턴트가 다루는 취업규칙, 인사평가 규정, 급여 테이블은
전부 이 범주에 해당합니다. 따라서 질의와 문서가 사내망을 벗어나지 않아야 합니다.

## 2. 목표 아키텍처

```
[사내 PC] --VPN/SSO--> [웹 앱]
                          |
                    [RAG 오케스트레이터]
                     |        |        |
              [임베딩 서버] [벡터DB] [LLM 서버]
               bge-m3      Qdrant    vLLM + Qwen3-32B
                          (온프렘)   (온프렘 GPU)
                          |
                   [문서 수집 배치] <- 사내 위키 / 그룹웨어
                          |
                   [감사 로그 DB]
```

모든 구성요소가 사내 네트워크 안에 있고, 외부로 나가는 트래픽은 없습니다.

## 3. 컴포넌트 선정

| 계층 | 프로토타입 (현재) | 온프렘 (목표) | 선정 이유 |
|---|---|---|---|
| 생성 모델 | 외부 API | Qwen3-32B 계열, vLLM 서빙 | 한국어 성능 대비 단일 GPU 서빙 가능한 크기 |
| 임베딩 | OpenAI text-embedding-3-small | bge-m3 | 다국어 지원, 로컬 서빙 가능 |
| 벡터 DB | numpy 브루트포스 | Qdrant | 청크 수천 개까지는 브루트포스로 충분하나, 문서가 늘면 메타데이터 필터 + HNSW 필요 |
| 앱 | Streamlit | 기존 사내 웹 스택 | 사내 SSO 연동 |
| 인증 | 역할 드롭다운 (데모용) | 사내 SSO + 인사시스템 직급 연동 | 역할 위조 방지 |

## 4. GPU 산정 (계산식 포함)

가중치 메모리 = 파라미터 수 x 파라미터당 바이트

- 32B 모델을 FP16으로 올리면: 32 x 2 = 약 64GB
- INT8/FP8 양자화하면: 32 x 1 = 약 32GB
- 여기에 KV 캐시와 실행 오버헤드로 20~30%를 더합니다.

결론: 80GB급 GPU 1장이면 FP8 양자화 기준으로 여유가 있고, FP16이면 빠듯합니다.
동시 사용자 50명, 사용자당 평균 1분에 1회 질의를 가정하면 초당 약 0.8 요청이며,
vLLM의 연속 배칭으로 GPU 1장에서 처리 가능한 수준입니다.

이 수치는 산식에 따른 개략 추정입니다. 확정 전에 실제 모델로 부하 테스트가 필요합니다.

## 5. 문서 갱신 파이프라인

규정 문서는 계속 개정됩니다. 오래된 조항을 근거로 답하는 것이 이 시스템의 최대 위험입니다.

1. 야간 배치로 사내 위키와 그룹웨어의 변경분을 감지합니다.
2. 변경된 문서만 재청킹하고 재임베딩합니다. (전체 재구축 금지, 비용 문제)
3. 각 청크는 `version`과 `effective_date`를 메타데이터로 가집니다.
4. 시행일이 지나지 않은 개정본은 검색 대상에서 제외합니다.
5. 답변에는 항상 근거 문서의 버전과 시행일을 함께 표시합니다.

## 6. 접근 제어와 감사

- 권한 필터는 **검색 단계**에서 적용합니다. 권한 없는 청크를 프롬프트에 넣은 뒤
  답변에서 가리는 방식은 프롬프트 인젝션 한 번에 원문이 노출됩니다.
- 모든 질의는 `data/access_log.jsonl` 형식으로 기록합니다:
  시각, 사번, 역할, 질문, 인용 문서, 거부 여부, 차단된 청크 수.
- 기밀 등급 문서가 인용된 질의는 별도 알림 대상으로 분류합니다.

## 7. SaaS 대비 비교

| 항목 | 외부 API | 온프렘 |
|---|---|---|
| 초기 비용 | 없음 | GPU 서버 도입 비용 |
| 운영 비용 | 토큰 종량제 | 전력, 상면, 운영 인력 |
| 보안 정책 부합 | 미부합 (DOC-SEC-005 제3조 위반) | 부합 |
| 모델 성능 | 상위 | 동급 오픈 모델 기준 다소 열위 |
| 응답 지연 | 네트워크 왕복 포함 | 사내망, 더 짧음 |

질의량이 적으면 API가 저렴하지만, 이 시스템에서는 비용이 아니라
보안 정책 부합 여부가 결정 요인입니다.

## 8. 단계별 도입

1. 1단계: 공개 등급 문서만, 외부 API로 파일럿 (현재 프로토타입)
2. 2단계: 임베딩만 사내로 이관, 생성은 API 유지
3. 3단계: 전면 온프렘 전환, 기밀 문서 인덱싱 개시
4. 4단계: 그룹웨어/위키 자동 연동, 야간 갱신 배치 상시화
