# On-premise 구축 설계서

> **필수 산출물 (B)**. `CLAUDE-hackathon-context.md` §2가 요구하는 "On-premise 환경 구축 방안"이다.
> 코드가 아니라 문서로 제출한다. 실제 온프레미스 인프라를 구축하지 않는다.
>
> 등장하는 사내 규정은 **(가상) 주식회사 케이넥스**의 더미데이터다. 실존 기업과 무관하다.
>
> 수치가 붙은 항목은 **계산식을 함께** 적었다. 실제 도입 전 자사 조건으로 재계산해야 한다.
> 참고 자료의 은행 도메인 임계값(환각률 1%, 유사도 0.92 등)은 근거 없이 옮기지 않았다.

## 1. 왜 온프렘인가

사내 정보보안 정책(`DOC-SEC-005` 제3조)은 고객 개인정보, 소스코드, 미공개 재무자료를
외부 생성형 AI 서비스에 입력하는 것을 금지한다.

그런데 온보딩 어시스턴트가 다루는 취업규칙, 인사평가 규정, 급여 테이블은 **전부 이 범주에
해당한다.** 특히 `DOC-HR-006`(인사평가)과 `DOC-HR-007`(보상 테이블)은 `confidential` 등급이다.

따라서 질의와 문서가 사내망을 벗어나지 않아야 한다.
**비용이 아니라 보안 정책 부합 여부가 결정 요인이다.**

### 1.1 프로토타입의 두 모드

프로토타입은 이미 두 모드를 갖고 있다 (`src/providers.py`).

| 모드 | LLM | 임베딩 | 외부 호출 | 용도 |
|---|---|---|---|---|
| **온프렘 모드** (기본) | Ollama 로컬 | BGE-M3 로컬 | **없음** | 제출·시연 |
| 클라우드 모드 | Anthropic / Upstage / OpenAI | Upstage / OpenAI | 있음 | 더미데이터 체험 |

클라우드 모드는 **더미데이터 전용**이며 사내 실데이터에 쓰지 않는다.
현재 어느 모드인지는 화면 사이드바에 항상 표시된다(`providers.mode_label`).
이것이 컨텍스트 문서 §4의 "외부 의존을 몰래 늘리지 않는다"를 이행하는 방법이다.

## 2. 목표 아키텍처

```
[사내 PC] --VPN/SSO--> [웹 앱]
                          |
                    [RAG 오케스트레이터]
                     |        |        |
              [임베딩 서버] [벡터DB] [LLM 서버]
               bge-m3      ChromaDB   vLLM + Qwen3-32B
               (온프렘)     (온프렘)    (온프렘 GPU)
                          |
                   [문서 수집 배치] <- 사내 위키 / 그룹웨어
                          |
                   [감사 로그 DB]
```

모든 구성요소가 사내 네트워크 안에 있고 외부로 나가는 트래픽이 없다.

### 2.1 네트워크 격리 경계

- 사용자 -> 웹 앱: 사내망 또는 VPN. 인터넷 노출 없음
- 웹 앱 -> 모델 서버: 내부 서브넷 전용. **외부 egress 차단**(방화벽 아웃바운드 deny 기본)
- 모델 가중치와 임베딩 모델은 **사전 다운로드 후 오프라인 반입**. 런타임에 허깅페이스로 나가지 않는다
- 이 egress 차단이 "몰래 외부 API를 부르는 코드"에 대한 마지막 방어선이다

## 3. 컴포넌트 선정

| 계층 | 프로토타입 (현재) | 온프렘 (목표) | 선정 이유 |
|---|---|---|---|
| 생성 모델 | Ollama 로컬(`qwen2.5:7b`), 없으면 API 폴백 | Qwen3-32B 계열, vLLM 서빙 | 한국어 성능 대비 단일 GPU 서빙 가능한 크기 |
| 임베딩 | **BGE-M3 로컬 (1024차원)** | 동일 | 다국어·한국어 상위권, 로컬 서빙 가능 |
| 어휘 검색 | kiwipiepy 형태소 + BM25 | 동일 | 순수 파이썬, GPU 불필요 |
| 벡터 DB | **ChromaDB** | ChromaDB 또는 Qdrant | §3.1 참조 |
| 앱 | Streamlit | 사내 웹 스택 | 사내 SSO 연동 |
| 인증 | 역할 드롭다운(데모용) | 사내 SSO + 인사시스템 직급 연동 | 역할 위조 방지 |

**임베딩 계층이 프로토타입과 온프렘에서 동일하다는 점이 중요하다.** 이관 시 재색인이 필요 없고,
프로토타입에서 측정한 검색 품질 수치가 온프렘에서도 그대로 유효하다.

### 3.1 벡터 DB: FAISS를 쓰지 않는 이유

**FAISS에는 메타데이터 필터가 없다.**

이 시스템의 권한 필터는 `src/store.py`에서 `where={"clearance": {"$in": [...]}}`로
**DB 질의 조건에 내려가 있다.** 권한 없는 청크는 후보 목록에 아예 오르지 않는다.

FAISS를 쓰면 전체를 검색한 뒤 애플리케이션 코드에서 걸러내야 한다. 그 순간
"검색 단계 필터링"이 "검색 후 필터링"으로 바뀌고, 필터를 빠뜨린 코드 경로가 하나만 있어도
기밀 문서가 새어나간다. **성능이 아니라 보안 때문에 메타데이터 필터가 있는 DB를 쓴다.**

규모가 커지면 Qdrant로 옮긴다. Qdrant도 페이로드 필터를 지원하므로 같은 구조가 유지된다.

### 3.2 하드웨어 요구사항

**GPU 산정 (계산식)**

가중치 메모리 = 파라미터 수 x 파라미터당 바이트

- 32B FP16: 32 x 2 = **약 64GB**
- 32B FP8/INT8: 32 x 1 = **약 32GB**
- KV 캐시와 실행 오버헤드로 **20~30%** 추가

결론: **80GB급 GPU 1장**이면 FP8 기준 여유가 있고, FP16이면 빠듯하다.

**처리량 가정**: 동시 사용자 50명, 사용자당 1분에 1회 질의 -> 초당 약 0.8 요청.
vLLM 연속 배칭으로 GPU 1장에서 처리 가능한 수준이다.

**임베딩 서버**: BGE-M3(568M)는 CPU로도 동작한다. 청크 수천 개 규모에서 GPU는 불필요하며,
GPU를 쓰면 색인 시간만 짧아진다.

**디스크**: 모델 가중치 약 65GB(32B FP16) + 임베딩 모델 2.2GB + 벡터 DB(청크 1만 개 x 1024차원
x 4바이트 = 약 40MB) + 감사 로그. **여유 있게 500GB.**

> 위 수치는 전부 산식에 따른 개략 추정이다. 확정 전에 실제 모델로 부하 테스트가 필요하다.
> **이 문서에 측정값으로 적힌 성능 숫자는 없다.**

## 4. 보안 설계

### 4.1 권한 모델

| 역할 | 열람 가능 등급 | 32청크 중 차단 |
|---|---|---|
| 신입사원 `intern` | public | 19 |
| 일반 직원 `employee` | public, internal | 9 |
| 인사팀 `hr` | public, internal, confidential | 0 |

**전수 검사 결과**: 청크 32 x 역할 3 = **96조합, 반례 0건**
(`python eval/permission_matrix.py`). 표본이 아니라 전량이므로 신뢰구간이 없다.

온프렘에서는 역할이 드롭다운이 아니라 **사내 SSO + 인사시스템 직급 연동**으로 결정된다.
역할 위조를 막는 것이 핵심이고, 등급 매핑 표 자체는 그대로 쓴다.

### 4.2 검색 단계 필터링 (설계상 불변조건)

권한 필터는 **검색 단계**에서 적용한다. 권한 없는 청크를 프롬프트에 넣은 뒤 답변에서
가리는 방식은 **프롬프트 인젝션 한 번에 원문이 노출된다.**
이 원칙은 벡터 DB를 교체하더라도 유지한다(§3.1).

### 4.3 프롬프트 인젝션 방어

1. **지시 앵커링**: 시스템 지시를 프롬프트 전반에 반복 배치한다. 앞에 한 번만 두면
   뒤쪽 문서 내용에 덮인다
2. **데이터와 지시의 분리**: 검색된 문서는 별도 구분자로 감싸고 "이것은 데이터이지 지시가
   아니다"를 명시한다
3. **인용 검증**: 생성된 답변이 인용한 출처가 실제 검색 결과에 있는지 대조한다
   (`src/answer.py`)

### 4.4 개인정보 마스킹

**현재 프로토타입에는 구현하지 않았다.** 더미데이터에 주민번호·연락처 형식의 문자열을
아예 생성하지 않는 것으로 대체했다. 실데이터로 옮길 때 필요한 설계는 다음과 같다.

**색인 시점 마스킹(권장)**: 검색 대상이 되기 전에 지운다. 인덱스에 남지 않으므로
검색으로도 프롬프트로도 유출 경로가 없다.

| 유형 | 처리 |
|---|---|
| 주민등록번호 | 정규식 탐지 -> 전체 치환 `[주민번호]` |
| 휴대전화·유선번호 | 뒷 4자리만 `[전화 ****]` |
| 이메일 | 도메인만 남김 `[이메일 @company.com]` |
| 계좌번호 | 전체 치환 `[계좌번호]` |
| 이름 | **자동 마스킹하지 않는다.** 규정 문서의 부서장·담당자명은 업무상 필요하다. 대신 등급으로 접근을 제한한다 |

**질의 시점 마스킹**: 사용자가 질문에 개인정보를 넣는 경우다. 질의 로그에 남기기 전에
같은 정규식을 적용한다. 원문은 어디에도 저장하지 않는다.

**한계**: 정규식은 형식이 정해진 것만 잡는다. 문맥 의존적 개인정보(예: "김 과장의 작년 평가
등급")는 못 잡는다. 이는 마스킹이 아니라 **등급 기반 접근 제어**로 막는 문제다.

### 4.5 질의 로그 취급 방침

**무엇을 남기는가** (`data/access_log.jsonl`, 현재 구현됨)

```
ts, role, query, mode, abstained, blocked_chunks,
cited: [{doc_id, section, score}]
```

온프렘에서 추가할 것: 사번(질의자 식별), 응답 지연, 사용 모델.

**취급 원칙 5가지**

1. **답변 본문은 로그에 남기지 않는다.** 인용된 `doc_id`와 `section`만 남긴다.
   답변 본문을 남기면 로그 DB가 곧 기밀 문서의 사본이 된다
2. 질의문에는 §4.4의 마스킹을 적용한 뒤 저장한다
3. **보존 기간**: 감사 목적 1년, 이후 자동 삭제. 통계용으로는 개인 식별자를 제거한 집계본만 남긴다
4. **접근 권한**: 로그 열람은 정보보안팀과 감사 담당으로 제한한다. **인사팀도 기본 제외다.**
   질의 로그는 "누가 무엇을 궁금해했는가"이므로 그 자체가 민감정보다
5. **기밀 등급 인용 알림**: `confidential` 문서가 인용된 질의는 별도 알림 대상으로 분류한다

### 4.6 Rate Limit

역할별 분당 질의 수를 제한한다. 목적은 둘이다.

- GPU 자원 보호 (동시 사용자 50명 가정에서 한 사용자가 독점하지 못하게)
- **기밀 문서 대량 추출 시도 탐지.** 짧은 시간에 `confidential` 인용이 반복되면 차단하고 알린다

구체 수치는 실사용 분포를 본 뒤 정한다. **지금 숫자를 적으면 근거 없는 값이 된다.**

## 5. 문서 갱신 파이프라인

규정 문서는 계속 개정된다. **오래된 조항을 근거로 답하는 것이 이 시스템의 최대 위험이다.**

1. 야간 배치로 사내 위키·그룹웨어의 변경분을 감지한다
2. **변경된 문서만** 재청킹·재임베딩한다 (전체 재구축 금지, 비용 문제)
3. 각 청크는 `version`과 `effective_date`를 메타데이터로 가진다 (현재 구현됨)
4. 시행일이 지나지 않은 개정본은 검색 대상에서 제외한다
5. 답변에는 항상 근거 문서의 **버전과 시행일**을 함께 표시한다

청킹은 고정 길이가 아니라 `## 제N조` 헤딩 단위다. 조항 번호를 그대로 출처로 쓰기 위해서이며,
개정이 조항 단위로 일어나므로 **재색인 범위도 조항 단위로 좁아진다.**

## 6. Kafka

> **결정: 프로토타입에 구현하지 않는다. 이 문서에만 기술한다** (`CLAUDE.md` §9).
> 아래는 "도입한다면 이렇게 한다"의 설계이지 구현 계획이 아니다.

**구현하지 않는 이유 3가지**

1. 동시 사용자 수십 명 규모에서 Kafka의 강점(높은 처리량, 수평 확장)이 **발동할 조건이 없다**
2. 비동기 구간이 생기면 **트레이스 기반 진단 경로가 끊긴다.** 관측성이 이 주제의 강점 축인데
   이를 약화시킨다
3. 브로커 운영 부담이 **시연 리스크**를 키운다

### 6.1 문서 인제스트 파이프라인

사규 개정 이벤트를 토픽에 발행하고 컨슈머가 파싱 -> 청킹 -> 임베딩 -> 업서트를 처리한다.
프로듀서와 컨슈머를 분리하면 **인제스트 부하가 챗봇 응답 경로에 영향을 주지 않는다.**

### 6.2 감사 추적 (레코드 Header, Interceptor)

레코드 Header에 생성 위치 정보를 실어 **메시지를 파싱하지 않고도 출처를 추적**한다.
Interceptor로 표준 헤더 삽입과 민감정보 삭제를 클라이언트 코드 변경 없이 수행한다.
§4.5의 감사 요구에 직접 대응한다.

### 6.3 로그 다중 소비

동일 QA 로그를 세 컨슈머 그룹이 각각 **전량** 수신한다:
운영 지표(Loki) / 평가 파이프라인(Ragas) / 감사 보관.
**소비처가 3곳 이상이 되는 시점이 도입의 실질적 분기점이다.**

### 6.4 신뢰성 설정

- `acks` 수준(0/1/all): 감사 로그는 유실이 곧 감사 실패이므로 **`all`**
- `enable.idempotence`로 정확히 한 번 쓰기
- 옵셋 커밋이 어긋나면 중복 처리 또는 누락이 생긴다. 인제스트는 멱등 업서트라 중복에 안전하고,
  감사 로그는 누락이 더 위험하므로 **중복을 감수하고 재처리**하는 쪽을 택한다

### 6.5 격리

다중 클러스터로 데이터 유형별 분리. 감사 로그와 운영 지표를 같은 클러스터에 두지 않는다.

### 6.6 용량 계획

**컨슈머 수가 파티션 수를 초과하면 초과분은 메시지를 받지 못한다.**
파티션 수를 처음부터 여유 있게 잡는다. 나중에 늘리면 키 기반 순서 보장이 깨진다.

### 6.7 도입 판단 기준선

| 조건 | 판단 |
|---|---|
| 동시 사용자 수십 명, 단일 서버 | **불필요** (현재 여기) |
| 문서 소스가 여러 개이고 갱신이 잦음 | 인제스트 큐로 검토 |
| 로그 소비처 3곳 이상 | 도입 근거 성립 |
| 감사 로그 보존 의무 발생 | 도입 근거 성립 |
| 다중 인스턴스 수평 확장 | 도입 |

### 6.8 Java 자료를 Python으로 옮길 때의 주의

참고 자료의 Kafka 내용은 **전부 Java 클라이언트 기준이다.**
API 이름과 테스트 도구(`MockAdminClient` 등)가 Python 클라이언트에 그대로 대응되지 않는다.
**Java 코드를 그대로 옮기지 말고 개념 수준으로 기술한다.**

## 7. 관측성

### 7.1 해커톤 범위

로그는 `logs/YYYY-MM-DD.json`에 JSON Lines로 남긴다. 필드명은 변형하지 않는다.

```
latency_ms, ttft_ms, input_tokens, output_tokens, tokens_per_second,
estimated_cost_usd, avg_retrieval_score, answer_length, cache_hit
```

트레이싱은 **Arize Phoenix self-host**. **현재 미착수다.**

**진단 순서** (아무 데나 먼저 보지 않는다)

| 증상 | 확인 순서 |
|---|---|
| 느리다 | `ttft_ms` -> `cache_hit` |
| 비용이 높다 | `estimated_cost_usd` -> `input_tokens` |
| 답변이 엉뚱하다 | `avg_retrieval_score` **먼저** -> 그다음 프롬프트 렌더링 결과 |
| 에러 | Phoenix 트레이스로 끊긴 지점 확인 |

"답변이 엉뚱하다"에서 검색 점수를 먼저 보는 이유는, 대부분의 엉뚱한 답이 생성 문제가 아니라
**검색이 엉뚱한 문서를 준 결과**이기 때문이다. 프롬프트부터 고치면 원인을 지나친다.

### 7.2 확장 시: Loki / Promtail / Grafana

해커톤 범위에서는 제외한다. 확장 시 붙이는 방법만 적는다.

- Promtail이 `logs/*.json`을 수집 -> Loki 적재 -> Grafana 대시보드
- Phoenix는 **개별 질의의 추적**, Grafana는 **전체 추세**를 본다. 역할이 다르므로 둘 다 필요해진다
- 도입 시점: 운영자가 "어제보다 느려졌나"를 묻기 시작할 때. 그전에는 과잉이다

## 8. SaaS 대비 비교

| 항목 | 외부 API | 온프렘 |
|---|---|---|
| 초기 비용 | 없음 | GPU 서버 도입 비용 |
| 운영 비용 | 토큰 종량제 | 전력, 상면, 운영 인력 |
| **보안 정책 부합** | **미부합** (`DOC-SEC-005` 제3조 위반) | **부합** |
| 모델 성능 | 상위 | 동급 오픈 모델 기준 다소 열위 |
| 응답 지연 | 네트워크 왕복 포함 | 사내망, 더 짧음 |
| 데이터 주권 | 벤더 의존 | 완전 통제 |

질의량이 적으면 API가 저렴하다. 그러나 이 시스템에서는 **비용이 아니라 보안 정책 부합
여부가 결정 요인이다.** 위 표에서 굵게 표시한 행 하나가 나머지를 무의미하게 만든다.

## 9. 단계별 도입

| 단계 | 범위 | 외부 의존 |
|---|---|---|
| 1 | 공개 등급 문서만, 클라우드 모드 파일럿 | 임베딩·생성 모두 외부 |
| 2 | **임베딩만 사내로 이관**(BGE-M3 로컬), 생성은 API 유지 | 생성만 외부 |
| 3 | **전면 온프렘 전환**, 기밀 문서 인덱싱 개시 | 없음 |
| 4 | 그룹웨어·위키 자동 연동, 야간 갱신 배치 상시화 | 없음 |

**현재 프로토타입은 2단계와 3단계 사이에 있다.** 임베딩은 이미 로컬 BGE-M3가 기본이고,
생성은 Ollama가 1순위이되 개발 머신에 Ollama가 없어 실행이 확인되지 않았다.

기밀 문서 인덱싱을 3단계로 미루는 이유는, 권한 필터가 전수 검사로 검증된 뒤에야
`confidential` 등급을 인덱스에 올려도 안전하기 때문이다. **검증은 이미 끝났다**(§4.1).

## 10. 운영

### 10.1 사규 개정 반영 절차

1. 인사팀이 위키에 개정본을 올린다 (`version`, `effective_date` 필수)
2. 야간 배치가 변경분을 감지하고 해당 조항만 재색인한다
3. 시행일 전까지는 검색 대상에서 제외된다
4. 시행일 이후 자동 활성화. **구 버전은 삭제하지 않고 비활성 보관**한다 (감사 대응)

### 10.2 재색인 전략

- **전체 재색인이 필요한 경우**: 임베딩 모델 교체 시에만. 모델이 바뀌면 벡터 공간이 달라져
  기존 인덱스와 섞을 수 없다
- **부분 재색인**: 문서 개정 시. 조항 단위로 좁혀진다
- 재색인 중에도 구 인덱스로 서비스한다. 완료 후 원자적으로 교체한다

### 10.3 백업과 복구

- **원본 문서**: 위키가 원본이므로 별도 백업 불필요. 인덱스는 **재생성 가능한 파생물**이다
- **감사 로그**: 별도 백업 필수. 유실이 곧 감사 실패다
- 복구 목표: 인덱스는 재색인으로 복구(수 분~수십 분). 감사 로그는 무손실

### 10.4 장애 대응

| 장애 | 동작 | 사용자에게 보이는 것 |
|---|---|---|
| LLM 서버 다운 | 검색까지만 수행 | 근거 문서 목록은 표시, 답변 생성만 실패 |
| 임베딩 서버 다운 | **BM25로 자동 강등** | 검색 계속 동작. 방식이 바뀌었음을 표시 |
| 벡터 DB 다운 | 서비스 중단 | 점검 안내 |

**임베딩 서버가 죽어도 BM25로 계속 동작한다는 점이 중요하다.** 이 구조는 프로토타입에
이미 구현돼 있고(`src/providers.py`의 능력 매트릭스), 온프렘에서도 그대로 유지한다.

## 11. 미결 사항

- **Ollama 실동작 미확인.** 온프렘 모드의 기본 생성 백엔드인데 개발 머신에 설치되지 않아
  `src/llm.py`의 Ollama 경로가 한 번도 실행되지 않았다
- **한국어 생성 모델 미확정.** `qwen2.5:7b`를 기본값으로 잡아뒀을 뿐 비교 평가하지 않았다
- **Phoenix 트레이싱 미착수.** `logs/` 디렉터리도 아직 없다
- **Rate Limit 수치 미정.** 실사용 분포를 보기 전에는 근거 없는 값이 된다
- **개인정보 마스킹 미구현.** §4.4는 설계이며 코드가 없다
- GPU 산정은 전부 산식 추정이다. **부하 테스트를 하지 않았다**
